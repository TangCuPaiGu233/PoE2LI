> **负责人**：远岫（架构师）
> **版本**：v1.0
> **状态**：Sprint 1 已发布
> **适用**：PoE2LI 全团队

---

## 一、核心理念

**「够用就好，但接口要为未来留余地」**

每次 review 本质是在回答三个问题：
1. **这个改动对吗？**（正确性）
2. **这个改动好吗？**（设计质量）
3. **这个改动安全吗？**（风险控制）

---

## 二、PR 基本规范

### 2.1 PR 粒度

| 维度 | 红线 | 说明 |
|------|------|------|
| 改动行数 | ≤ 400 行 | 超过必须拆分为多个 PR |
| 改动文件 | ≤ 15 个 | 超过说明变更范围过大 |
| 逻辑变更 | 1 个 | 一个 PR 只做一件事 |
| 连带重构 | ❌ 禁止 | 重构单独提 PR |

> **例外**：全局配置变更、依赖升级、自动化格式化等机械性变更可适当放宽。

### 2.2 PR 必备内容

每个 PR 必须包含：
1. **描述**：What + Why（必要时加 How）
2. **关联任务/Issue**：链接到 Backlog 任务（如有）
3. **本地验证结果**：截屏或日志片段
4. **测试覆盖**：新增或修改的测试
5. **检查清单**（见下文）

## 三、Review Flow

```
[Author] 创建 PR
    │
    ▼
[Author] 自检（跑过检查清单）
    │
    ▼
[Peer]  同级 Review
    │  ├── 前端→前端，后端→后端
    │  ├── AI→AI，数据→数据
    │  └── 跨模块变更同时 @ 相关工程师
    │
    ├── [Architect] 架构影响 Review ← 仅架构级变更需要
    │     └── 新模块/新依赖/接口变更/数据模型变更
    │
    ▼
[QA]    QA 闸门审查 ← 按 QA Gate 计划触发
    │
    ▼
[Merge] 合并
```

### 3.1 各环节职责

| 环节 | 谁 | 做什么 | 耗时目标 |
|:----:|:---:|--------|:--------:|
| 自检 | PR 作者 | 逐条过 Checklist，确认无遗漏 | 作者自行控制 |
| Peer Review | 同领域工程师 | 代码正确性、可维护性、风格一致性 | ≤ 4 项目时 |
| Architect Review | 远岫 | 架构合理性、接口设计、技术债评估 | ≤ 2 项目时 |
| QA Gate | 半山居 | 按 QA 节点定义执行审计 | 按 QA 计划 |

## 四、Review Checklist（五轴评审法）

每个 PR 在 Merge 前，作者必须自检 + Review 者逐条确认。

### 🔷 轴一：正确性（Does it work?）

- [ ] 代码实现了需求描述的功能？
- [ ] 边界条件已覆盖（空值、负数、超长输入、并发竞态）？
- [ ] 错误路径有处理（try/except 是否恰当）？
- [ ] 日志记录足够定位问题？

### 🔷 轴二：设计（Is it the right approach?）

- [ ] 这个变更是否符合现有架构方向（见 CLAUDE.md 架构原则）？
- [ ] 是否引入了不必要的依赖或抽象？
- [ ] 接口设计是否为未来扩展留了余地（不过度设计）？
- [ ] 模块职责是否单一？

### 🔷 轴三：可维护性（Will we understand this in 6 months?）

- [ ] 命名清晰自文档化（不需要注释解释变量名）？
- [ ] 复杂逻辑有注释说明 Why（而非 What）？
- [ ] 配置项已提取到位（无硬编码 magic number/string）？
- [ ] 类型注解完整（Python 函数签名、TypeScript 类型）？

### 🔷 轴四：测试（What evidence do we have?）

- [ ] 新功能有对应测试覆盖？
- [ ] 修复的 Bug 有 regression test？
- [ ] 测试独立可重复（不依赖外部服务/状态）？
- [ ] 手动测试结果已附在 PR 描述中？

### 🔷 轴五：安全（What happens when things go wrong?）

- [ ] 外部输入已校验/清洗？
- [ ] API 鉴权/访问控制已考虑？
- [ ] 用户数据无泄露风险（日志/报错不泄露敏感信息）？
- [ ] 降级策略已定义（失败时是否友好提示）？

## 五、Merge 规则

| 条件 | 说明 |
|------|------|
| 📌 至少 1 个 Peer Approval | 同领域工程师 Approve |
| 📌 Checklist 全绿 | 五个轴全部确认 |
| 📌 CI 绿 | pytest + lint 通过 |
| 📌 无未解决的对话 | 所有 Comment 已 Resolve |
| 📌 架构级变更需远岫 Approve | 接口/数据模型/新依赖变更 |

**合并方式**：Squash & Merge（保持 main 历史干净）

**谁可合并**：
- 普通 PR：Peer Reviewer 或 PR 作者（获得 Approve 后）
- 架构级 PR：仅远岫或朝露

## 六、Review 文化守则

### 对 Review 者

1. **批评代码，不批评人** — "这段逻辑有竞争条件" 而非 "你写错了"
2. **给出理由** — "不建议这样做，因为..." 而非 "改掉"
3. **分清主次** — 架构问题 blocking，风格问题 non-blocking，可以 approve 后追
4. **48 小时内响应** — 收到 Review 请求后在 48 项目时内给出反馈
5. **小 PR 快速过，大 PR 拆了再过** — 400 行以上的 PR 直接要求拆分

### 对 PR 作者

1. **尊重 Review 者时间** — PR 描述写好，自检完再请求 Review
2. **每个 Comment 必须有回应** — Accept / 反驳（带理由）/ 追问
3. **不要强行合入** — 如果 Review 者有合理担忧，先解决再合并
4. **区分 blocking / non-blocking** — 标记清楚哪些 comment 必须解决

## 七、Review 优先级

紧急程度由 织墨（PM）标记，远岫确认：

| 优先级 | 响应时间 | 适用场景 |
|:------:|:--------:|----------|
| P0 | ≤ 2 项目时 | 生产阻断修复、关键路径阻塞 |
| P1 | ≤ 8 项目时 | Sprint 里程碑交付 |
| P2 | ≤ 1 项目日 | 常规功能 PR |
| P3 | ≤ 2 项目日 | 文档/配置/重构/非紧急变更 |

## 八、QA Gate 衔接

此文档是半山居输出《QA 审核流程文档》的输入。QA 闸门在以下节点介入：

1. **PR Merge 前** — 对关键路径 PR 做质量抽审
2. **Release 前** — 完整回归验证
3. **每周审计** — 代码库健康度检查（测试覆盖率、技术债、安全扫描）

QA Gate 的具体定义、检查清单、通过标准由半山居在 QA 节点定义文档中详细输出。
