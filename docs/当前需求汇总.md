## 二、发现的问题

### 1. kb_entities 实体库严重不全
- PoE2 有 12 个职业、36 个升华，库内只有 5 个职业、6 个升华
- 女猎手（Huntress）、行者（Spirit Walker）、猎巫人（Witchhunter）等核心实体缺失
- 根因：实体不是从结构化数据灌入的，而是从文本 chunk 中用 NLP 词典匹配提取的。词典不全 → 大量实体漏掉

### 2. 实体关系缺失
- kb_edges 中没有"哪个升华属于哪个职业"的关系边
- kb_edges 中没有"哪个词缀能出现在哪个基底上"的约束边
- 导致 Agent 把猎巫人推荐给女猎手（猎巫人属于佣兵）

### 3. 检索质量
- baseline 幻觉率仍然偏高（build_001 有 bone construct/unearth 残影）
- 百科类（扭曲项链/畸变项链）仍然混淆
- 延迟 57s，仍有优化空间

## 三、待解决的需求

### 需求 1：实体库全量重建（P1）
**目标**：不再依赖 NLP 提取，从源头结构化全量采集，一个不漏。

**做法**：
- 从 poe2db.tw 爬所有技能/装备/升华/职业/基底/词缀的结构化列表
- 直接灌入 kb_entities，不经过文本匹配过滤
- 建 entity 之间的关系边（class→ascendancy, base→mod, skill→support_gem 等）

### 需求 2：中英文 + 腾讯服国服映射（P1）
**目标**：统一的中文名查询链，腾讯服译名差异有兜底。

**分层方案**：
- 第一层：Trade API 官方中英对照表（`trade_items_en_cn.json`，~2876 条，每次赛季更新刷新）
- 第二层：poe2db.tw 三语数据（爬取时直接提取 name_cn 写入 kb_entities）
- 第三层：腾讯服差异小表（手工维护几十条，如"扭曲项链 vs 畸变项链 vs 扭曲护身符"）
- 查询链：Trade API → poe2db entities → 腾讯覆盖表，按优先级走

**要点**：第一层为主力（数据最权威），第三层只补少数特例，不反向污染主表。

### 需求 3：词缀-基底映射
**目标**：用户问"重革腰带能出什么词缀"时，系统能回答前缀和后缀分别有哪些。

**需要**：
- 从 Trade API stat 索引中提取 item_class_restriction
- 或从 poe2db.tw 解析 mod 页面的适用范围
- 建立 mod ↔ base item 的 kb_edge 关系

### 需求 4：检索精度提升（P0-B 未完部分）
**目标**：延迟 <30s，幻觉率进一步下降。

**做法**（待实施）：
- RRF 分层融合（精确匹配 vs 向量检索，按 intent 选策略）
- BGE reranker（候选 top-30 重排取 top-8）
- concept_links 受控扩展（仅精确未命中时触发）

## 四、技术决策

| 决策 | 结论 |
|------|------|
| kb_entities 来源 | 结构化爬取 poe2db.tw，不用 NLP 从 chunk 提取 |
| 中文映射 | Trade API 官方索引为主，poe2db 三语为辅，腾讯差异小表兜底 |
| 实体校验 | AgentClaimGuard 模式：Claim → Evidence → Verdict |
| eval 优先级 | 所有优化前先跑 eval 拿基线，改完再跑看 diff |
