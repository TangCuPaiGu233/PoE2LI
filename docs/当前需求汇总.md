## 二、发现的问题

### 1. kb_entities 实体库严重不全
- PoE2 有 12 个职业、36 个升华，库内只有 5 个职业、6 个升华
- 女猎手（Huntress）、行者（Spirit Walker）、猎巫人（Witchhunter）等核心实体缺失
- 根因：实体不是从结构化数据灌入的，而是从文本 chunk 中用 NLP 词典匹配提取的。词典不全 → 大量实体漏掉

### 2. 实体关系缺失
- kb_edges 中没有"哪个升华属于哪个职业"的关系边
- kb_edges 中没有"哪个词缀能出现在哪个基底上"的约束边
- 导致 Agent 把猎巫人推荐给女猎手（猎巫人属于佣兵）

### 3. 检索质量
- baseline 幻觉率仍然偏高（build_001 有 bone construct/unearth 残影）
- 百科类（扭曲项链/畸变项链）仍然混淆
- 延迟 57s，仍有优化空间

## 三、待解决的需求

### 需求 1：实体 + 关系全量重建（P1）
**目标**：不再依赖 NLP 从文本提取，从 poe2db.tw 结构化全量爬取，保留页面间的层级和关联字段，直接灌入 kb_entities + kb_edges。数据源有的关系，我们就都有。

**为什么必须这样做**：游戏内的关系远不止"职业→升华""基底→词缀"两种，还包括但不限于：
- 技能 → 辅助宝石（supports）
- 技能 → 所需武器类型
- 暗金 → 基底装备
- 装备 → 自带基底词缀
- 宝石 → 标签（攻击/法术/范围/投射物等）
- 通货 → 效果
- 天赋节点 → 属性加成
- 地图 → Boss → 专属掉落池
- ……

逐一列举永远列不全。正确做法是**让数据源的结构驱动覆盖范围**——poe2db.tw 每个页面都有明确字段和层级关系，结构化爬取后直接灌入 kb_edges，不需要人脑枚举。

**做法**：
- 从 poe2db.tw 爬所有实体类型的结构化页面（技能/装备/升华/职业/词缀/基底/通货/天赋…）
- 保留页面间的关联字段（如技能页面的 `supports`、装备页面的 `tags`/`implicit`、升华页面的上级职业）
- 直接灌入 kb_entities（带 `name_cn`/`name_en`/`entity_type`）和 kb_edges（带 `relation` 类型）
- 不经过 NLP 文本匹配——源头有什么，库就有什么

### 需求 2：中英文 + 腾讯服国服映射（P1）
**目标**：统一的中文名查询链，腾讯服译名差异有兜底。

**分层方案**：
- 第一层：Trade API 官方中英对照表（`trade_items_en_cn.json`，~2876 条，每次赛季更新刷新）
- 第二层：poe2db.tw 三语数据（爬取时直接提取 `name_cn` 写入 kb_entities）
- 第三层：腾讯服差异小表（手工维护几十条，如"扭曲项链 vs 畸变项链 vs 扭曲护身符"）
- 查询链：Trade API → poe2db entities → 腾讯覆盖表，按优先级走

**要点**：第一层为主力（数据最权威），第三层只补少数特例，不反向污染主表。

### 需求 3：词缀-基底映射（P1）
**目标**：用户问"重革腰带能出什么词缀"时，系统能回答前缀和后缀分别有哪些。

**需要**：
- 从 Trade API stat 索引中提取 item_class_restriction
- 或从 poe2db.tw 解析 mod 页面的适用范围
- 建立 mod ↔ base item 的 kb_edge 关系

### 需求 4：玩家经验知识注入（P1）
**目标**：数据库能够承载非结构化的玩家经验性知识，弥补 AI 在实战经验上的不足。不依赖文档结构，而是从玩家撰写的攻略/心得中提取经验碎片灌入数据库。

**背景**：
- 当前知识库主要为官方数据（poe2db 百科、poe2wiki、PoB 构建数据），覆盖了"事实"但缺少"经验"
- 玩家经验来源种类繁多：开荒攻略、配装心得、物价趋势、BD 对比、赛季变化感受、特定机制的实战技巧……
- 覆盖的游戏模块庞杂，无法预定义所有经验类型

**设计要求**：
- 知识库 schema 必须支持灵活的"经验片段"——不预设固定的 chunk_type，允许自由标签
- 灌入管线支持多种来源格式（Markdown 文档、纯文本对话、结构化 Q&A 对、截图标注…）
- 经验性知识应标注"来源"（哪位玩家）/ "赛季版本" / "主观度"（硬数据 vs 个人观点），以便后续检索时根据可信度加权
- 实体关系图（kb_edges）支持经验关系的扩展——比如玩家会说"这把武器在实战中比另一把更好用"，这是一种主观比较边，与官方数据的关系边共存但权重不同

### 需求 5：检索精度提升（P0-B 未完部分）
**目标**：延迟 <30s，幻觉率进一步下降。

**做法**（待实施）：
- RRF 分层融合（精确匹配 vs 向量检索，按 intent 选策略，详见 PoE2LI-解决思路3.0.md 附录 B.1）
- BGE reranker（候选 top-30 重排取 top-8）
- concept_links 受控扩展（仅精确实体未命中时触发）

## 四、数据库扩展性设计

### 核心原则

**不靠人脑枚举所有关系类型。数据源的结构驱动覆盖范围，经验注入用灵活 schema 兜底。**

### Schema 设计要点

**knowledge_chunks 表**（已存在，需扩展）：
- 当前 `chunk_type` 为枚举值（wiki/pob/poe2db/homework…），随着玩家经验加入需要改为自由标签
- 需增加字段：`author`（来源玩家/来源 URL）、`subjectivity`（主观度等级：0=硬数据, 1=半主观, 2=纯个人感受）、`season`（赛季标记）

**kb_entities 表**（已存在）：
- 当前 entity_type 已覆盖 skill/item/mod/mechanic/ascendancy/class 等，足够用于结构化数据
- 新增 entity_type：`experience_snippet`（经验片段）、`player_opinion`（玩家观点）

**kb_edges 表**（已存在）：
- 当前 relation 类型：mentions/provided_by/is_a
- 结构化数据爬取后新增：`belongs_to`（职业→升华）、`supports`（辅助宝石→技能）、`applies_to`（词缀→基底）、`drops_from`（掉落关系）等——由 poe2db.tw 页面结构自动生成，不需要枚举
- 经验数据使用更灵活的 relation：`better_than`（主观比较）、`works_with`（搭配经验）、`avoid_for`（避坑提示）、`seasonal_tip`（赛季特定）等——随着经验注入自然生长，不预设封闭集合

## 四、技术决策

| 决策 | 结论 |
|------|------|
| kb_entities 来源 | 结构化爬取 poe2db.tw，不用 NLP 从 chunk 提取 |
| 中文映射 | Trade API 官方索引为主，poe2db 三语为辅，腾讯差异小表兜底 |
| 实体校验 | AgentClaimGuard 模式：Claim → Evidence → Verdict |
| eval 优先级 | 所有优化前先跑 eval 拿基线，改完再跑看 diff |
