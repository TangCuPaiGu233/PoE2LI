# PoE2LI 项目运维现状摸底报告

> 编写时间：项目时间第 0 天  
> 范围：代码仓内现有部署/运维相关文件梳理，不含线上实测  
> 目的：识别现状与可改进缺口，供后续运维体系升级参考

---

## 1. Docker 环境

### 现状
- 主编排：`docker-compose.yml`
  - 服务：`postgres(pgvector/pg15) / redis / backend / celery_worker / celery_beat / frontend / langfuse / langfuse-clickhouse`
  - 依赖链通过 `depends_on + healthcheck` 实现启动顺序
  - 仅将项目内 `./data` 绑定到容器内 `/app/data`；代码 baked into image
- 腾讯云专用 override：`docker-compose.tencent.yml`
  - 去除 `postgres/redis` 对外端口映射，限制 memory limits
  - 为 `celery_worker` 加 `profiles: celery`，避免小实例误启
- 现有容器：
  - `poe2li-backend`：FastAPI + uvicorn
  - `poe2li-frontend`：Next.js
  - `poe2li-postgres`：pgvector 版
  - `poe2li-redis`
  - NAS 文档记录为 5 个容器，主仓 compose 实际包含 8 个服务（含 langfuse/clickhouse/celery）

### 关键特征
- 环境变量以 compose 文件内联形式配置，大量引用 `${VAR}` 但未在 repo 中提供实际值
- backend / celery_worker 重复维护环境变量，存在维护风险
- 生产环境曾用 `docker cp` 热修 backend，修改后未回到镜像体系
- 腾讯云还通过 `docker update --memory=...` 绕过 compose V2 内存限制限制

## 2. CI/CD

### 现状
- 仓库内未找到 `.github/workflows` / `.gitlab-ci.yml` / `Jenkinsfile` / `circleci`
- 部署方式：
  - NAS：本地脚本 `deploy_nas.py`（paramiko SSH 调用 Docker）
  - 腾讯云：`scripts/deploy_tencent.py`（SSH → git pull → build → up → pg_restore 可选）
- 发布流程文档：`docs/ops/deployment.md`
  - 分支约定 `main` 或 `cursor/cn-trade-realm`
  - 采用“NAS 开发/测试 → 腾讯云生产”模式

### 风险
- 无自动化 CI：合并代码到 main 不会自动触发构建、测试、部署
- 无发布制品仓库（ghcr / harbor 等），镜像每次现场 build，不可复现
- 密钥/凭据依赖本地 `.env`，且 deploy_tencent.py 把 NAS `.env` 直接复制到腾讯云（ stripping 代理变量后）

## 3. 环境配置

### 现状
- `.env.example` 存在，实际 `.env` 未纳入仓库
- 环境变量来源多样：
  - `docker-compose.yml`
  - `docker-compose.tencent.yml`
  - `backend/Dockerfile` 内硬编码清华 pip 源
- 运行参数：
  - `CHAT_RUNTIME` 支持 `legacy` / `orchestrator`
  - `ORCHESTRATOR_MAX_PARALLEL` / `CHAT_TRADE_SEARCH_MAX`
- 腾讯云通过 override 文件去除代理变量，并关闭部分端口

### 风险
- `.env.example` 虽不可读（安全规则限制），但 compose 中有硬编码默认值 `LANGFUSE_INIT_PASSWORD=admin123`、`NEXTAUTH_SECRET` 默认值
- `HTTP_PROXY` / `HTTPS_PROXY` 内联写死 NAS 内网地址
- 无 `.env` 变更追踪：无法知道某次线上问题由哪次环境变量变更引起

## 4. 数据库

### 现状
- 主库：`pgvector/pgvector:pg15`
  - 向量检索使用 BGE-M3 1024 维
  - 已有约 7204 条 trade stats、~22K chunks、24 张游戏数据表
- 迁移：`alembic`；entrypoint 在容器启动时自动 upgrade / stamp
- Langfuse 自建使用同一 PostgreSQL，另有一张 `langfuse_langfuse` 库 + ClickHouse 用于 event

### 备份与恢复
- 未发现 cron / scheduled backup 配置
- 存在一次性同步能力：`deploy_tencent.py` 中 `SYNC_NAS_DATA=1` 会从 NAS `pg_dump` → 腾讯云 `pg_restore`
- 未发现持续增量备份策略；若磁盘/容器损坏，无自动恢复机制

## 5. 日志 & 监控

### 现状
- 日志：容器 stdout/stderr；backend 通过 `logging.basicConfig(INFO)` 输出到控制台
- 无集中式日志收集（ELK / Loki / 云日志）
- 监控：无 Prometheus / Grafana / 黑盒探针
- AI 可观测：Langfuse 已集成（traces/spans），但仅覆盖 AI 调用链路，不覆盖容器、数据库、队列
- 无告警规则（无 health 失败告警 / 队列堆积 / 磁盘使用率 / API 错误率）

## 6. 安全

### 现状
- 密钥管理：
  - `.env` 本地管理，未纳入 Vault / CI Secrets / 云 KMS
  - 文档中记录了 SSH 密码（NAS：`SKChaidao@123`，腾讯云：`SKChaidao123`）
- 端口暴露：
  - NAS：`3000 / 5433 / 6379 / 8000`
  - 腾讯云：仅文档要求放通 TCP 3000，但 nginx 反向代理到 3000
- 网络：
  - `docker-compose.yml` 中 `CORS` 允许所有来源、允许凭证
- TLS：生产域名目前仅 HTTP，未配置 HTTPS
- Langfuse 默认 admin 口令 `admin123`，加密 key 默认 64 个 0

## 7. 运维缺口（优先级列表）

### 缺口 1（高）：缺少自动化 CI/CD，发布依赖本地脚本 + 人工操作
- 影响：合并代码后无自动验证；部署可复现性差；密钥通过脚本跨机器传递
- 建议：
  - 建立 GitHub Actions / GitLab CI 流水线，覆盖 lint / pytest / build image / push registry
  - 使用镜像制品库（ghcr / harbor），消除现场 build
  - `.env` 由环境/密钥管理系统注入，禁止脚本跨机拷贝

### 缺口 2（高）：缺少生产级数据库备份策略
- 影响：NAS/腾讯云任一节点磁盘/容器损坏，可能导致知识库、构建数据永久丢失
- 建议：
  - 增加定时 `pg_dump` 到持久目录或对象存储（保留 7/30 天）
  - 对 pgvector 大表定期检查向量索引有效性
  - 记录 `restore drill` 演练流程

### 缺口 3（高）：安全基线不达标（密钥暴露、默认口令、CORS、无 HTTPS）
- 影响：文档泄露账号密码；Langfuse 默认口令易被爆破；中间人攻击风险
- 建议：
  - 将账号密码从文档移除，改为 Vault/CI Secrets/受限文档
  - Langfuse 初始化口令、NEXTAUTH_SECRET、ENCRYPTION_KEY 必须强制随机化
  - 生产启用 HTTPS（Let's Encrypt）；CORS 收紧为实际前端域名

### 缺口 4（中）：无基础设施监控与告警
- 影响：服务不可用/队列堆积/磁盘满需要人工发现
- 建议：
  - 引入轻量探针：容器健康、`/health` 接口、数据库连接、Redis 内存
  - 错误追踪：考虑 Sentry / 自建，至少把 FastAPI 异常结构化输出到日志
  - 告警接入企业微信/钉钉/邮件

### 缺口 5（中）：环境变量与多环境配置分层混乱
- 影响：代理变量、LLM 供应商、内存限制散落多文件；腾讯云通过“删除代理变量”实现差异化
- 建议：
  - 引入严格分层：`.env.example` → `compose` defaults → 环境 override
  - NAS/腾讯云差异全部收口到对应 override + 少量 `.env`，不再内联代理 IP

### 缺口 6（低）：Docker 镜像热修流程不可追溯
- 影响：`docker cp` 修改代码后未回写仓库，镜像重建会丢失
- 建议：
  - 建立 hotfix 分支流程：所有热修必须走 git 后再 rebuild
  - 保留 `docker cp` 作为最终应急手段，但需创建工单并 24h 内回写仓库

## 9. 结论

当前 PoE2LI 已具备“可运行”的 Docker 部署与基本文档，但运维体系处于“手工作坊”阶段：
- 发布靠脚本 + 人工；
- 无 CI/CD、无备份策略、无监控告警；
- 安全基线存在明显硬伤（默认口令、明文密码、无 HTTPS）。

建议按 **缺口 1/2/3** 优先推进：先上 CI/CD 和镜像制品，建立备份策略，收紧密钥与网络暴露。
