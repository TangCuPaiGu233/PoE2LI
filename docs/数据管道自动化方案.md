## 二、当前更新策略与问题

### 2.1 GGPK / SC 导出
- **现状**：全手动，需本地安装 PoE2 客户端，导出后手动 copy 到 NAS 数据目录。
- **问题**：版本更新时易遗漏；无自动化校验；TC/SC/EN 一致性依赖人工 eyeball。

### 2.2 爬虫类（poe2db / wiki / caimogu）
- **现状**：脚本分散，无统一调度；部分脚本无幂等保护，重复执行可能产生重复数据。
- **问题**：数据源失效时排查成本高；无统一重试/告警。

### 2.3 Trade API 双语数据
- **现状**：`fetch_trade_items_bilingual.py` 和 `fetch_trade_stats_bilingual.py` 为一次性脚本，输出静态 JSON。
- **问题**：赛季变更后 stat ID 可能变化，静态文件会过期；无自动更新机制。

### 2.4 poe.ninja / 价格扫描
- **现状**：Celery beat 已配置每日 06:00 扫描；`daily_filter_update.py` 可手动触发。
- **问题**：生产环境 `celery_beat` 在腾讯云默认不启用；扫描结果无质量校验。

## 三、自动化方案设计

### 3.1 总体策略

**原则**：优先用现有工具编排，不引入重型调度器；分阶段落地，Sprint 1 只出方案不动底层重构。

**建议工具栈**：
- **编排层**：Makefile / shell script（NAS 本地） + 现有 Celery beat（已部署）
- **校验层**：Python 校验脚本（post-export / post-ingest）
- **调度层**：cron（NAS）或 Celery beat（Docker 内）
- **告警层**：日志 + 可选 webhook（Sprint 2）

### 3.2 各数据源更新策略

| 数据源 | 更新策略 | 建议频率 | 自动化方式 | 优先级 |
|--------|----------|----------|------------|--------|
| GGPK / SC | 全量替换 | 版本更新时 | Makefile target + 校验脚本 | P0 |
| TC 补导出 | 全量补跑 | TC 修复后一次性 | Makefile target | P0 |
| Trade items/stats | 全量刷新 | 赛季变更/每月 | Makefile target + cron | P1 |
| poe2db | 增量/全量 | 每周或按需 | 统一 scraper 基类 + cron | P2 |
| poe2wiki | 增量/全量 | 每周或按需 | 统一 scraper 基类 + cron | P2 |
| caimogu | 增量/全量 | 每月或按需 | 统一 scraper 基类 + cron | P2 |
| poe.ninja | 增量拉取 | 每日 | Celery beat（现有） | P1 |
| 价格扫描 | 增量扫描 | 每日 | Celery beat（现有）+ 手动 trigger | P1 |

### 3.3 建议的自动化编排

```
NAS 数据更新入口（Makefile / shell）
│
├── make data-ggpk-export
│   ├── export_en_tc.py --ggpk ... --output ...
│   ├── extract_sc.py --bundles ... --output ...
│   └── verify_data_completeness.py  ← 新增校验脚本
│
├── make data-tc-fix
│   ├── export_en_tc.py --tables <tc_missing_tables>
│   └── verify_data_completeness.py
│
├── make data-trade-sync
│   ├── fetch_trade_items_bilingual.py
│   ├── fetch_trade_stats_bilingual.py
│   └── verify_trade_mappings.py  ← 新增校验脚本
│
├── make data-poe2db-ingest
│   ├── scrape_poe2db_v3.py
│   ├── ingest_poe2db.py
│   └── verify_kb_counts.py  ← 新增校验脚本
│
├── make data-wiki-ingest
│   ├── crawl_poe2wiki.py
│   ├── backfill_links.py

│
└── make data-daily
    ├── scan_base_prices_task (Celery)
    ├── generate_filter (Celery)
    └── verify_filter_output.py  ← 新增校验脚本
```

### 3.4 校验脚本设计

每个数据更新流程后增加极简校验，确保：
1. **文件数/行数 sanity check**：`tc/`、`sc/`、`en/` 文件数与关键表非空。
2. **关键字段存在率**：如 `Mods.json` 的 `Name` 字段非空比例、`Stats.json` 的 `Id` 存在。
3. **映射覆盖率**：Trade items/stats 的 EN→CN 匹配率不低于阈值。
4. **KB 入库计数**：ingest 前后 `knowledge_chunks` 行数变化符合预期。

校验失败时：
- 打印差异明细到日志
- 返回非零退出码
- 可选：发送通知到飞书/钉钉 webhook（Sprint 2）

### 3.5 与现有部署流程集成

现有 NAS 部署脚本 `deploy_nas.py` 和 `docs/ops/deployment.md` 已定义数据路径 `/volume1/docker/PoE2LI/data/`。

建议在 NAS 数据目录下新增 `scripts/` 子目录存放 Makefile 和校验脚本，由运维人员在版本更新时手动触发，或接入 cron。

## 六、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|:----:|:----:|------|
| GGPK 导出依赖本地客户端 | 高 | 中 | 仅 NAS 执行；导出产物纳入版本控制或备份 |
| 爬虫源失效 | 中 | 中 | 统一基类 + 重试 + 降级标记 |
| 校验脚本误报 | 中 | 低 | 阈值可配置；失败时输出差异明细便于人工判断 |
| Celery beat 生产不启用 | 已知 | 中 | 价格扫描保留手动 trigger；Sprint 2 确认 beat 配置 |
